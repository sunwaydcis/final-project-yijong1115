# Personal Reflection
Developing the Food Pantry Inventory and Demand Management System helped me understand how object-oriented programming concepts can be applied in a complete desktop application rather than only in small classroom exercises. At the beginning, I focused on creating a simple ScalaFX window and navigation structure. As the project developed, I gradually added inventory management, household requests, stock monitoring and distribution planning. Working in small sections made the project easier to test and allowed me to commit each meaningful change to Git.

One of the most important things I learned was how to design a clear domain model. I used the `Entity` trait as a shared contract and created a sealed `FoodItem` hierarchy with `PerishableFood` and `ShelfStableFood`. Their different expiry behaviour and storage instructions demonstrated subtype polymorphism and method overriding. I also used a bounded generic `Repository[T <: Entity]` so the same CRUD contract could support food items, household requests and distribution plans. Immutable case classes and the `copy` method helped me update records without using mutable domain variables.

The most challenging part was maintaining consistency between related records. A distribution plan affects the available food quantity and the status of a household request. My earlier version only changed the distribution status, which could leave the inventory and request records inconsistent. I improved this by creating a transaction-based allocation workflow using Apache Derby. Creating a distribution plan reserves the required stock. Completing the plan deducts the stock exactly once, while cancelling it releases the reservation. The linked household-request status is also kept consistent with its active allocations. This taught me why database transactions are important when several updates must either succeed together or fail together.

I also faced smaller technical problems during development. Testing Derby through `sbt console` caused a class-loader issue, so I tested database initialisation through the normal forked application instead. I encountered a UTF-8 BOM error when creating a Scala file through PowerShell and learned to write files without the BOM. Later, I corrected category case sensitivity, replaced free-text stock units with validated choices and changed the dashboard because adding packs, bottles and kilograms into one total was not meaningful.

Testing became more important as the application grew. I added MUnit tests for food validation, category normalisation, household request decisions, dashboard summaries, distribution reports and the main distribution workflow. These tests helped confirm that completion reduces stock only once, cancellation preserves stock and invalid status transitions are rejected. The ScalaFX interface was also improved with CSS, clearer forms, confirmation dialogs, automatic refreshing and visible feedback messages.

Overall, this project improved my confidence in Scala 3, ScalaFX, inheritance, generics, immutable programming, JDBC persistence and testing. I learned that good software design is not only about making features work, but also about separating responsibilities, protecting data consistency and giving users clear feedback. With more time, I would add search and filtering, configurable alert thresholds and a more detailed reporting screen.
